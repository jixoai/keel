# Before/after — Windows first start

## v0.6.0 published asset (before)

- **No-argument first start**: runtime extracted, PostgreSQL 18 initialized and
  `ready to accept connections`, but `127.0.0.1:13750` never listened; the keel
  process stayed alive with no CPU growth. 180s timeout.
  Raw: `04a-start-hang-diagnosis.txt`.
- **`keel db start` on the existing cluster**: exit 124 after a 20s timeout,
  while PostgreSQL was already listening on `127.0.0.1:13741`.
  Raw: `04c-db-start-repro.txt`.
- **Root cause**: `startDevDBCluster` ran `pg_ctl -w start` through
  `CombinedOutput()`. Windows `pg_ctl` daemonizes the postmaster, which inherits
  the stdout/stderr pipe write end; `CombinedOutput` waits for EOF forever.
- **Also found after the PG fix**: fresh `keel serve` reported `/v1/ready` 503
  `missing tables: runtime_instances, handoffs` (separate change
  `fix-serve-ready-schema`).

## 0.6.1 fixed build (after)

- **`keel db start` on a fresh `KEEL_HOME`**: exit 0 in 3s, database created,
  PostgreSQL listening on `127.0.0.1:13741`.
- **No-argument start on a fresh `KEEL_HOME`**: `/v1/health` 200 after 1.6s,
  `/v1/ready` 200 after 0.1s, both `127.0.0.1:13750` and `127.0.0.1:13741`
  listening. See `../../fix-serve-ready-schema/evidence/fixed-ready.txt`.
- **Windows regression test**: `TestStartPGDaemonDoesNotWaitForInheritedStdio`
  and `TestStartPGDaemonErrorNamesLogs` PASS on the Windows test binary
  (`regression-test-windows.txt`).
