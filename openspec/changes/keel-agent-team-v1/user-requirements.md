## 2026-11-11 · 设置页、Provider、预设、插件与 UI

> 设置面板需要单独一个整个页面，参考 zcode。
> 模型的配置，首先要配置 providers，这样重点参考 zcode，可以同时配置多个 provider。
> 但 zcode 这边的配置是远远不够的，作为下一代 Agent ，我们要做的是更复杂的配置。
>
> 首先是模型的支持我们还得支持这几种 provider 的配置: 图片生成（参考 HermesAgent 的gen-image 插件）、视频升成（参考 HermesAgent 的 gen-video 插件）、决策模型（参考 SystemOne 的 jev 模型标准，以及重点参考 cloudflare 新出的决策模型标准）。
> 这些 provider，都是通过 plugin 来进行支持的。
> 所以你需要在 UI 层，提供 providers 的扩展能力。
>
> ---
>
> 接着，我们需要有一个特定的面板，是关于 provider 组合预设。我们可能配置了十几个供应商，接下来，通过预设，将其中几个组合在一起。这里的组合，还包含一些细节配置，比如某一个模型，但是调整它的上下文、思考强度，甚至是它的一些参数。这取决于 provider提供了多少的可调参数。
>
> ---
>
> 然后再到会话中，可以选中预设（或者跳转到设置页面去配置预设）。 选中之后，就意味着这个会话可以使用选中的这些模型。
> 而Keel的内核 AgentLoop，需要一个 LLM 模型，所以可以在预设中，选中一个 LLM-provider，从而开始对话。
>
> 这些预设的作用，是和一些功能相关联的，这些功能，自然会通过 bash 来提供 cli 能力，比如图片生成视频生成，或者调用决策模型等等，甚至包括使用 LLM 做一次性的调用，这也是可以的。
>
> ---
> 我说这么多，重点在于你需要把插件和界面都设计出来。
>
> 做界面设计的时候，你可以先从部件开始做设计，后面再组合起来。

## 2026-11-11 · 预设名称可填写、多生图用途、语音模型

> 我看到你在预设里面搞了什么“主 LLM”、“LLM 备选”，我希望这个名字是可以填写的，千万别跟我说这是写死的。一个预设是很灵活的，甚至需要描述这个模型配置是用来干嘛的，比如我甚至会配置 3 个生图模型，有的用来做场景，有的用来做精灵图，有的是用来改图的。等等。对了，你顺便把语音的模型也加上：文本转语音，和语音转文本的。

## 2026-11-11 · 从 sub-agent 转向 Agent / AgentTeam

> 关于 sub-agent，我好像有跟你提到过相关的插件吧，主要还是参考 zcode 的 subagent 的配置为基础。但我要跟你聊的是 Keel Harness 这里一个更先进的设计：不是 subagent。但 subagent 的能力是与生俱来的，只要我们提供了 agent-plugin。
>
> 我们把刚才那个模型预设，改掉，改成 agentTeam 预设。
>
> 首先，model-plugin: 刚才提到 modelProvider 这个配置，是可以配置各种模型的供应商，这方面已经提到过，我就不重复。
> 然后就是agent-plugn: 可以理解成“Agent”的配置，你别理解成“subagent”，你就直接理解成 Agent 智能体。这里也需要做各种配置，参考 Zcode 的预设方式，但只是参考，我们这边需要更加灵活：
> 1. 可以配置“默认模型”，zcode 是配置固定模型，我们这边配置只是默认模型
> 2. 可以配置工具能力，正如 zcode 那样，但 zcode 很基础，我们需要插件化地管理这些工具的能力，所以工具列表需要有一个注册源，从那里拿。
> 3. 可以配置一些系统提示词（AGENTS.md）
> 4. 可以配置头像、名字。我们这边的头像，默认使用 npm/github 自动升成头像那套
>
> ----
>
> 然后重点来了，把刚才那个“模型预设”，改成“agentTeam 设置”。
>
> 这里可以配置 AgentTeam 团队！
>
> 也就是说，需要一个 agent-team-plugin，由它来提供 agentTeam 的管理能力（包括 cli 和 ui）。agentTeam 有一个概念，就是一定要有队长。其余的是灵活自由的：在 agentProvider +modelProvider 的基础上，可以配置出各种各样的成员。
>
> 换句话说，我们的会话开始这里，可以选择启动模式：
> 标准模式，意味着单会话：需要选择模型，然后开始。但是因为我们 bash 提供了启动 agent 的能力，所以很简单的，这里自然会有 main-agent 通过参数启动 sub-agent 的方式。
> AgentTeam 模式：需要选择团队预设（这时候就不是模型预设了）。
>
> 但最神奇的地方是，agentTeamPlugin，有 cli！，也就是说你可以只配置一个队长，然后让队长自己通过 cli 创建成员。除非你把队长的 agent-team 这个 cli 能力禁用掉。否则它是可以自由组装自己的团队的

## 2026-11-11 · 插件 CLI 能力与子能力声明

> agentTeamPlugin，有 cli。同理 modelPlugin 也有 cli。同理 agentPlugin，也有 CLI（这点你应该知道，但是你之前的认知可能只局限于用 cli 启动 agent，但我想告诉你，甚至可以管理 Agent）
> modelPlugin 同理，可以用 cli 管理 model。
>
> ---
>
> 一个插件，需要用声明它有哪些能力（cli），以及子能力（sub-command）。并且描述这些能力的特性。这样才能被 很好地管理。

## 2026-11-11 · AgentTeam 的本质：配置空间与开箱即用的团队

> 队长通过 agent-team CLI 创建/移除成员时，改动落在哪里？一切皆文件，但我们的文件可以落地在数据库中。
>
> AgentTeam 的成员在运行时是什么拓扑？这决定 session/run、任务卡和上下文归属。
>
> 你这个问题我没看懂，你不要把问题想复杂了，Agentteam模式能做到的事情，普通模式也完全能做到，但是普通模式需要将配置落地到modelprovider和agentprovider配置上，会导致配置污染的问题。而AgentTeam provider提供了一个配置空间，在这里可以自由组合model和agent 并对它们做出微调。这些微调发配置不会污染到modelprovider和agentprovider。这是agentteam最直接的好处
>
> 进一步的，agentteam因为这种team配置的存在缺口，因此很容易开箱即用进行某种协作。
> 换作普通模式下，就需要手动做一些提示词或者配置才能做到类似的效果。agentteam则是把这些繁琐的配置在agentteam-provider这里给做了。
>
> 这种效果的核心区别在于：你是要从零磨合出一份团队，还是直接找到一个磨合好的团队直接使用。
