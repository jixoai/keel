## 2026-11-12 · provider 决定会话面板；补 realtime

> 我这边想到一个问题：
> 1. 一个会话，不同种类的 provider 应有不同的输入面板和会话面板。比如 LLM 的输入面板就是一个文本框，会话面板就是对话历史记录；realtime 的输入面板就是语音输入，会话面板就是语音输入转译出来的历史记录；
> 2. 我们缺了一个非常重要的 providerd 支持：realtime 模型。
>
> ---
>
> 我刚才说的第一点非常非常重要。我建议你快速跟进这个功能。我假设，比如我在普通模式下：
> 选择 Main-Agent 的模型，选了 realtime，那么就应该进入实时对话模式：“输入面板就是语音输入，会话面板就是语音输入转译出来的历史记录”

>
> 比如我用 image 模型，那么界面上出现的应该是关于 image 模型的能力体现，输入面板和会话面板应该围绕 ：生成、编辑、多轮编辑
>

## 2026-11-13 · Owner 纠正 realtime 语义

> realtime 这种 API，是实时对话的啊，不是你这种“转写”。你没了解接口吗？它是基于 WebSocket 的实时传输模式，不是录制

> 你这个错误的界面也不用浪费，我不是跟你说了吗，每一种Provider 都有自己的面板。至少有一些组件可以给语音转文字使用。你有安排子代理维护自己的一套组件库并保持测试吗？

### 由此确立的裁决

1. `realtime` surface MUST 是持续双向音频会话（WebSocket/WebRTC）：麦克风音频持续上行、模型音频持续下行并边收边播、VAD 断句、barge-in 打断；转写只是伴随事件，不是输入机制。
2. “点击说话 → 转写文本”是 **STT surface**，保留给 `stt` Provider，不得冒充 realtime。
3. 每个 Provider surface 拥有自己的组件目录、harness、测试与验收；不得共用一个“万能聊天壳”。
4. 真实 realtime 需要 Provider 传输与音频桥；未配置 Provider 时必须显示配置/错误态，不得用模拟对话冒充。
